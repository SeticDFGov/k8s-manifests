Resumo

  • Servidor: uma VM (ceticsv0002, 10.233.159.150) com Kubernetes k3s v1.33 de nó único (4 vCPU, cerca de 8 GB de memória). Só é acessível pela rede do GDF ou pela VPN.
  • Entrada: o ingress Traefik do k3s recebe subgd.df.gov.br (front), subgd-api.df.gov.br (API, Keycloak e ArgoCD) e endereços internos *.10.233.159.150.nip.io.
  • Aplicação: front em Angular com SSR e API em .NET. O login é só pelo Keycloak (OIDC, Authorization Code com PKCE); a senha não passa pela API.
  • Identidade: Keycloak 26.6.1, realm SISTEMA_GEDE, federado ao Active Directory gdfnet.df por LDAP (somente leitura). Usuários, perfis e acessos são geridos no Keycloak.
  • Dados: PostgreSQL fora do cluster (10.230.81.119:5432), com os bancos db_subtdcr (GeDê) e db_centralrelacionamento (extrator, Olhar DF e MeasureSoftGram).
  • Entrega: GitOps. O GitHub Actions publica a imagem no Docker Hub e grava a versão no k8s-manifests; o ArgoCD aplica no cluster sozinho. Nenhuma mudança é feita direto na VM.
  • Monitoramento: VictoriaMetrics com node-exporter e kube-state-metrics, visto pelo Grafana.

3. Fluxo de login (OIDC)

O front leva a pessoa à tela de login do Keycloak, que confere a senha no Active Directory. O front recebe um código, troca pelo token direto no Keycloak e chama a API com esse token. A API só valida o token; a senha nunca passa por ela.

4. Entrega contínua (GitOps)

Todo merge na branch principal do front ou da API gera uma imagem e grava a versão dela no repositório k8s-manifests. O ArgoCD confere o repositório a cada 3 minutos e aplica a mudança. Mudanças manuais no cluster são desfeitas pelo ArgoCD (selfHeal).
